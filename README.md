# База материалов: гидроизоляция и наливные покрытия

Расчёт условий нанесения, справочник совместимости слоёв и хранилище параметров
продуктов, в котором у каждого числа есть источник и статус достоверности.

## Быстрый старт

```bash
python -m matdb dew --air 12 --rh 75 --surface 9
```

```
Точка росы:             7.7 °C
Запас над точкой росы:  +1.3 K
Влажность у поверхности:    92 %
…
Запас меньше 3 K — по общему правилу наносить нельзя.
```

Тот же расчёт в браузере, без установки и без сети: откройте
[`web/dewpoint.html`](web/dewpoint.html) — один файл, работает с телефона на
объекте. Реализация сверена с Python до 1e-9.

## Команды

| Команда | Что делает |
|---|---|
| `matdb dew` | Точка росы, запас, влажность у поверхности, влагосодержание |
| `matdb check <материал>` | Можно ли наносить этот материал в этих условиях |
| `matdb schedule <материал>` | График отверждения при фактической температуре |
| `matdb compat <верх> <низ>` | Совместимость стыка |
| `matdb gaps` | Незаполненные поля (`--all`, `--family`) |
| `matdb status` | Готовность карточек, разбивка по семействам |
| `matdb queue` | Очередь на загрузку документов с адресами |

Пример с прогнозом остывания — случай, когда утром всё в допуске, а к вечеру нет:

```bash
python -m matdb check isoflex-pu-500 --air 16 --rh 70 --surface 17 \
    --moisture 3.0 --drop 6
```

Совместимость учитывает направление:

```bash
python -m matdb compat pu_1k_moisture bitumen   # нужен блокирующий слой
python -m matdb compat bitumen pu_1k_moisture   # другой вопрос, другой ответ
```

## Извлечение из TDS

```bash
python tools/extract_tds.py tds/isomat/isoflex-pu-500.pdf \
    --id isoflex-pu-500 --revision 2024-03 --write
```

Отчёт даёт на каждое число страницу и точную цитату, чтобы сверка с документом
занимала секунды:

```
ИЗВЛЕЧЕНО (статус tds — требует сверки человеком):
  application.dew_point_margin_k = 3.0 K   с. 2
      «3°C above the dew point»
  application.substrate_moisture_max_percent = 4.0 %   с. 2
      «moisture content must be less than 4%»
Метод замера влажности основания: CM-метод (с. 2)
```

Поведение подчинено тому же правилу, что и вся база:

- Два разных значения одного поля — **конфликт**, в карточку не пишется ни одно.
- Ненайденное поле остаётся пробелом, догадка не подставляется.
- «Application temperature» без указания, воздух это или основание, не
  раскладывается на два параметра — попадает в раздел «разнести вручную».
- Расход не разносится автоматически: «на слой» и «на систему» в TDS выглядят
  одинаково, а ошибка здесь кратна числу слоёв.
- Ручная правка человека не затирается повторным разбором.
- Ничто не получает статус `verified` — это делает человек.

Правила настроены на точность, а не на полноту: пропущенный параметр стоит пяти
минут работы, ошибочно извлечённый — протечки. Отдельным тестом закреплён
реальный случай, найденный при разработке: на фразе «between +5°C and +35°C and
at least 3°C above the dew point» правило захватывало первое число диапазона и
выдавало запас 5 K вместо 3 K.

## Главное правило

**В базе нет чисел без источника.** Каждый параметр несёт статус достоверности:

```json
"substrate_temp_min_c": {
  "value": 5, "unit": "°C", "status": "tds",
  "source": "tds:isomat/isoflex-pu-500@2024-03#p2"
}
```

Голое число загрузчик отвергает с ошибкой. Причина простая: неверно извлечённое
из даташита значение выглядит ровно так же убедительно, как верное. Разница
должна быть видна коду, а не только внимательному читателю.

Статусов пять — от `verified` (человек сверил с документом и подписался) до
`unknown` (параметра нет, и это записано явно, чтобы попасть в рабочую очередь).
Подробно: [`docs/DATA_MODEL.md`](docs/DATA_MODEL.md).

Из того же правила следуют три поведения, которые выглядят как неудобство и
являются смыслом:

- **Незнание не равно разрешению.** Нет правила для пары материалов — ответ
  «нет правила», а не «совместимо». Закреплено тестом.
- **Непроведённая проверка не проходит.** Нет замера влажности основания — общий
  вердикт не «можно».
- **Пересчёт понижает доверие.** Время, пересчитанное с +20 °C на +8 °C,
  получает статус `estimated`, даже если исходное было подтверждено человеком.

Продукты: ISOMAT, ALCHIMICA (HYPERDESMO), Sika (Sikalastic, Sikafloor, Ucrete),
MAPEI (Mapelastic), Henkel (Ceresit), Triflex, ТЕХНОНИКОЛЬ. Каждая карточка
несёт производителя, наименование, семейство, роль и адрес документа —
`matdb queue` выдаёт это как очередь на загрузку.

Причина отсутствия чисел конкретная: сетевая политика окружения, в котором
собирался проект, пропускает практически только GitHub — домены производителей
и агрегаторов документации возвращают 403. Порядок работы и объяснение — в
[`docs/FETCH_QUEUE.md`](docs/FETCH_QUEUE.md): скачать →
`tools/extract_tds.py --write` → сверка человеком.

Поисковая выдача при этом возвращала конкретные числа (расход, предел влажности,
межслойный интервал). В базу они не внесены: пересказ поисковой системы не
является источником — неизвестна страница, неизвестна редакция и неизвестно, к
какому варианту продукта относится значение. Показательно, что расход
«1,0–1,5 кг/м²» выдавался одинаково для ISOFLEX-PU 500 THIXO и для DTL, хотя это
разные материалы. Записанное так число стало бы неотличимо от извлечённого из
документа; тест `test_no_placeholder_numbers_leaked_into_data` следит, чтобы
этого не случилось и впредь.

Порядок заполнения и список полей — в
[`docs/TDS_CHECKLIST.md`](docs/TDS_CHECKLIST.md).

### Что дало заведение карточек

Не только очередь работ. Разбор реального ассортимента заставил уточнить модель:
битум-модифицированные полиуретаны (HYPERDESMO-PB-1K, Sikalastic-320 NS) не
укладывались в существующие семейства и выделены в `pu_bitumen`. Разница не
косметическая — у них противоположный вердикт на стыке с битумом:

```
$ python -m matdb compat hyperdesmo-classic bitumen
hyperdesmo-classic по bitumen: только через промежуточный слой

$ python -m matdb compat hyperdesmo-pb-1k bitumen
hyperdesmo-pb-1k по bitumen: условно совместимо
```

При этом семейство само отдаёт битум наверх, поэтому слой над ним получает
отдельное предупреждение о проступании пятен. Аналогично выделен `pu_1k_wb`:
полиуретан на водной основе сохнет испарением, и высокая влажность ему мешает —
в отличие от влагоотверждаемого, которому она нужна.

Правила совместимости (27 штук) заполнены на уровне химии семейств со статусом
`reference`. Они говорят, какой вопрос задать документу; ответ даёт документ.

## Границы применимости

Расчётное ядро опирается на физику и проверено по табличным значениям:
аппроксимация Магнуса в редакции Sonntag (1990), погрешность менее 0.4 % в
диапазоне −45…+60 °C. Ему можно доверять в пределах этого диапазона.

Всё остальное — нет:

- Порог 3 K над точкой росы — общее правило лакокрасочных работ, а не требование
  конкретного продукта. Подставляется, только когда TDS молчит.
- Правило Q10 (удвоение времени на каждые 10 °C) даёт порядок величины. За
  пределами 0…40 °C расчёт отказывается работать, а не экстраполирует.
- Свойства семейств — уровень учебника. Конкретный продукт может вести себя
  иначе за счёт модификаторов.
- Влажность основания не пересчитывается между шкалами: соответствия между
  весовым методом, CM и показаниями влагомера в общем виде не существует.

Расчёт не заменяет решение человека на объекте. Проверить извлечённое из TDS
число может только тот, кто держал этот материал в руках.

## Разработка

```bash
python -m pytest tests/ -q
```

Зависимостей нет — только стандартная библиотека; `pytest` нужен для тестов.
Новая карточка:

```bash
python tools/new_material.py --id <id> --name "…" --manufacturer "…" \
    --family pu_1k_moisture --role membrane
```
