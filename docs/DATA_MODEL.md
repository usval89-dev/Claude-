# Модель данных

## Значение с происхождением

В базе нет голых чисел. Каждый параметр — объект:

```json
{
  "value": 5,
  "unit": "°C",
  "status": "tds",
  "source": "tds:isomat/isoflex-pu-500@2024-03#p2",
  "note": "раздел «Условия нанесения»"
}
```

Причина: неверно извлечённое из даташита число выглядит ровно так же
убедительно, как верное. Единственная защита — сделать разницу видимой на уровне
типа данных, а не примечанием мелким шрифтом. Загрузчик отвергает голое число
(`"substrate_temp_min_c": 5`) с ошибкой: значение, принятое молча, получает то же
доверие, что и проверенное.

### Статусы

| Статус | Что означает | Можно ли публиковать как факт |
|---|---|---|
| `verified` | Человек сверил с TDS и подтвердил, указав себя и дату | Да |
| `tds` | Извлечено из TDS, не перепроверено | Нет, только с пометкой |
| `reference` | Общее свойство химического семейства из литературы | Нет, это ориентир |
| `estimated` | Расчёт внутри базы (например, пересчёт времени по Q10) | Нет |
| `unknown` | Параметра нет. Явная дыра, а не отсутствующее поле | — |

Ограничения проверяются при создании значения, а не при выводе:

- `tds` и `verified` требуют `source`;
- `verified` дополнительно требует `verified_by` — у числа должен быть человек;
- `unknown` не может нести значение;
- любой другой статус обязан нести значение.

Метод `Value.require_trusted()` бросает исключение на всём, кроме `verified` —
для кода, который не имеет права работать с неподтверждёнными данными.

### Почему `unknown` — это поле, а не его отсутствие

`unknown` попадает в отчёт `matdb gaps` и становится строкой рабочей очереди.
Отсутствующее поле не попадает никуда. Разница между «мы не знаем» и «мы не
задумывались» — это разница между работой и её видимостью.

## Пересчёт понижает доверие

`adjust_time()` пересчитывает паспортное время на фактическую температуру по
правилу Q10 (реакция вдвое медленнее на каждые 10 °C холоднее). Результат всегда
получает статус `estimated`, **даже если исходное значение было `verified`**:
пересчёт — модель этой базы, а не данные производителя.

За пределами 0…40 °C пересчёт не выполняется вовсе и возвращает «нет данных» с
объяснением. Экстраполировать эмпирическое правило на мороз — это выдавать
выдумку за расчёт.

## Совместимость

Правило — направленная пара:

```json
{
  "over": "family:pu_1k_moisture",
  "under": "family:bitumen",
  "verdict": "needs_primer",
  "rationale": "…",
  "conditions": ["…"],
  "primer_families": ["epoxy_2k"],
  "status": "reference"
}
```

`over` — что кладём, `under` — на что. Обратное направление описывается
**отдельной записью**: полиуретан по битуму и битум по полиуретану — разные
вопросы с разными ответами.

Стороны — либо `family:<имя>`, либо `product:<id>`. Разрешение идёт от частного к
общему: правило для пары продуктов побеждает правило для пары семейств.

### Незнание — не разрешение

Если правила для пары нет, ответ — `unknown`, и он `blocking`. Отсутствие записи
никогда не превращается в `compatible`. Это главное свойство движка, и оно
закреплено тестом: справочник, который на незнакомый вопрос отвечает «наверное,
можно», опаснее отсутствия справочника.

## Готовность карточки

`Material.readiness()` отвечает, можно ли по карточке принимать решение на
объекте. Требуется, чтобы пять ключевых полей `application` были заполнены и
подтверждены:

- `substrate_temp_min_c`, `substrate_temp_max_c`
- `dew_point_margin_k`
- `substrate_moisture_max_percent`
- `ambient_rh_max_percent`

`matdb status` показывает эту сводку по всей базе. Карточка без TDS — нормальное
стартовое состояние, но она честно помечена как непригодная, и `matdb check` по
ней вернёт «нет данных», а не «всё хорошо».

## Проверка условий: отсутствие данных не проходит

`check_application()` возвращает список проверок с уровнями `ok` / `warn` /
`stop` / `no_data`. Итоговый вердикт `can_apply` истинен только когда **все**
проверки `ok`. `no_data` не проходит: непроведённая проверка не считается
пройденной.

Отдельный вход `expected_temp_drop_k` моделирует остывание основания за время,
пока плёнка открыта, — случай, когда утренний замер проходит, а вечерний уже нет.

## Что база принципиально не делает

- Не хранит числа, которых нет в документах.
- Не пересчитывает между шкалами влажности основания — соответствия между
  весовым методом, CM и показаниями конкретного влагомера в общем виде не
  существует.
- Не заменяет решение человека. Все команды заканчиваются напоминанием об этом,
  и это не юридическая формальность: продукт про ответственность за протечку не
  может опираться на уверенность расчёта.
