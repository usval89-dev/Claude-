# Что вытаскивать из TDS

Список полей, которые нужны, чтобы карточка отвечала на вопрос «можно ли класть
сейчас». Порядок — по важности: первые пять определяют, будет ли материал вообще
участвовать в расчёте.

Правило одно: **если параметра в документе нет — поле не заполняется.** Пустое
поле попадает в отчёт `matdb gaps` и когда-нибудь будет закрыто. Придуманное
значение не попадает никуда и будет использовано как настоящее.

## Обязательный минимум

| Поле | Где обычно в TDS | На что влияет |
|---|---|---|
| `application.substrate_temp_min_c` | «Условия нанесения», «Application conditions» | Нижняя граница работ |
| `application.substrate_temp_max_c` | там же | Верхняя граница; выше — резкое падение жизнеспособности |
| `application.dew_point_margin_k` | там же, часто формулировкой «не менее 3 °C выше точки росы» | Главный критерий допуска |
| `application.substrate_moisture_max_percent` | «Подготовка основания» | Отслоения и пузыри |
| `application.ambient_rh_max_percent` | «Условия нанесения» | Вспенивание влагоотверждаемых составов |

Без этих пяти команда `matdb status` пометит карточку как непригодную для
решения на объекте, и это правильно.

## Влажность основания — отдельное предупреждение

Число без метода замера бессмысленно. «4 %» весового метода и «4 %» CM-метода —
разные состояния бетона. Метод всегда пишется в `note`:

```json
"substrate_moisture_max_percent": {
  "value": 4, "unit": "%", "status": "tds",
  "source": "tds:manufacturer/product@2024-03#p2",
  "note": "CM-метод"
}
```

Если TDS даёт предел в единицах прибора (например, по шкале конкретного
влагомера) — так и записывать, не пересчитывая. Пересчёт между шкалами зависит
от состава бетона и в общем виде не существует.

## Времена

| Поле | Замечание |
|---|---|
| `cure.reference_temp_c` | **Без него все остальные времена нельзя пересчитать.** TDS почти всегда приводит времена при +20 °C, но пишет об этом мелким шрифтом внизу таблицы |
| `cure.reference_rh_percent` | Для влагоотверждаемых составов значим не меньше температуры |
| `cure.overcoat_min_h` | Раньше — слой «плывёт» |
| `cure.overcoat_max_h` | Позже — нужна шлифовка; часто указывается как «не более 48 часов», легко пропустить |
| `cure.pot_life_min` | Только для многокомпонентных; сильно зависит от температуры смеси |
| `cure.full_cure_d` | Момент, с которого можно давать эксплуатационную нагрузку и воду |

## Расход

`consumption.per_coat_kg_m2` и `consumption.coats` — расход **на слой** и число
слоёв. Частая ошибка извлечения: в TDS указан суммарный расход системы, а
записывается как расход на слой. Если в документе одно число без уточнения —
писать в `total_kg_m2`, а не в `per_coat_kg_m2`.

Расход в TDS дан для гладкого основания. На шероховатой стяжке фактический
выше, и это не повод править карточку — это повод написать об этом в `note`.

## Ссылка на документ

```json
"tds": {
  "url": "https://…",
  "revision": "как напечатано в документе",
  "issued": "2024-03",
  "retrieved": "2026-07-31"
}
```

Редакция обязательна. Производители меняют параметры между версиями молча, и
«данные из TDS» без указания какой именно — это данные неизвестного возраста.
Поле `retrieved` показывает, когда документ в последний раз открывали: через год
его стоит перечитать.

## Порядок работы

1. Открыть TDS, сохранить в `tds/<производитель>/<продукт>.pdf`.
2. Скопировать `data/materials/_TEMPLATE.json`, назвать по `id`.
3. Заполнить поля со статусом `tds`, указав страницу в `source`.
4. `python -m matdb status` — увидеть, чего не хватает.
5. Человек сверяет числа с документом и меняет статус на `verified`, проставляя
   `verified_by` и `verified_at`.

Шаг 5 нельзя автоматизировать. Он и есть содержание работы: извлечение — это
десять минут, а ответственность за число берёт тот, кто его подтвердил.
